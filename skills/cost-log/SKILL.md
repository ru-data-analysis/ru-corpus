# Журнал затрат

Чтобы решать, какую модель, какой объём и какую частоту прогонов можно себе позволить, нужны измеренные
цифры, а не ощущение. Навык оборачивает команду, замеряет её и дописывает строку в журнал.

## Запуск с замером

```bash
python scripts/cost_log.py run --log runs/cost.csv --label индексация-корпуса \
       --docs 15 --pages 266 --model "локальная, CPU" -- ru-corpus index
```

После `--` идёт обычная команда. Скрипт запускает её, передаёт вывод как есть, возвращает её код возврата
и записывает строку:

| Колонка | Смысл |
|---|---|
| `ts_utc`, `label`, `cmd` | когда, под каким именем, что запускалось |
| `exit` | код возврата команды |
| `wall_s` | время по часам |
| `cpu_s` | процессорное время потомков (пользователь + система); на Windows не измеряется |
| `max_rss_mb` | пиковая память самого тяжёлого потомка |
| `docs`, `pages` | объём обработанного, если указан; даёт цену на документ и страницу |
| `model`, `note` | описание модели или условий |

## Итоги и строка для отчёта

```bash
python scripts/cost_log.py summary runs/cost.csv [--label индексация-корпуса]
python scripts/cost_log.py line    runs/cost.csv --label индексация-корпуса
```

- `summary` — по каждой метке: число запусков, суммы времени, средние, секунды на документ и на страницу.
- `line` — последняя строка по метке в виде `cost: wall_s=…; cpu_s=…; max_rss_mb=…`; её вставляют в
  §1 рабочего отчёта (`analysis-spec-first`).

## Что помнить

- Замер относится к конкретной машине; в `note` полезно записать процессор и объём памяти.
- Неудачный прогон тоже записывается (`exit` ≠ 0): время впустую — тоже затрата.
- Скрипт ничего не знает о стоимости токенов внешних моделей: для них ведите журнал по счёту поставщика.
- Журнал — обычный CSV; открывается в таблице и хранится рядом с отчётами, а не в открытом репозитории,
  если в `cmd` могут оказаться пути закрытого корпуса.
